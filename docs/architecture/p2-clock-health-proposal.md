21 October 2026. **Owner approved offline prototype implementation.** This is the next
provider contract required by the [health review](p2-clock-health-review.md).
The owner approved the earlier offline guard and now the offline prototype below,
not installing or operating a time daemon, a host collector, real trust material

## Recommended next scope

Implement an **offline Linux/Chrony collector + independently signed evidence
prototype**. Use recorded/fake daemon responses, injected clock readings,
temporary signing keys and private temporary state. No daemon installation,
privileged container, host-clock change, real credential, new server, Snowflake
call, public deployment or automatic startup. Keep current live routes disabled.
An existing Linux host is needed only for later separately approved acceptance;
do not buy or provision one to complete this offline prototype.

Chrony is a proposed source, not assumed to exist on the developer's macOS host
or Docker VM. Real host/version/source configuration remains unselected. The
prototype must not replace missing health with synchronized=true or a local clock.

## Trust and collection boundary

- A trusted host-side collector, outside the app workers, is the only proposed
  recipient of the new health signing private key. It is distinct from broker
  assertion signing and every TLS/DB/Snowflake credential. Workers receive only
  an explicitly pinned health verification key and host/generation configuration.
- Collection uses one fixed, reviewed, read-only monitoring command against the
  host-local daemon. No application-selected executable, command, socket/server,
  DNS, environment options, fallback endpoint, retry or unbounded subprocess.
  Pin the daemon/CLI version and exact monitoring transport before real use.
- Do not give workers the daemon control socket, host network, Docker socket,
  clock-setting privilege or a new network time client. Monitoring permission
  and daemon configuration must be inspected separately on the eventual host.
- A fixed signed-evidence delivery mechanism is reviewed with file/secret
  custody later. Signature validation does not establish safe mounts or protect
  a compromised host. No real signing key is generated by this proposal.

## Proposed evidence and consumer checks

Use a separate strictly parsed RS256 envelope, with a fixed algorithm and no
key discovery. Bind it to the configured host, boot/clock domain and health
generation; reject caller-selected keys, algorithms and unknown/extra fields.
Include collector epoch/sequence, collection interval, monotonic and suspend-
aware timestamps, source/reference freshness, synchronization/leap status and
conservative integer-nanosecond uncertainty. No patient/application payloads.

The consumer must independently sample its matching clock domain and verify
signature, binding, collection duration and freshness. Re-reading or re-signing
an old measurement must not make the source reference fresh. Persist accepted
epoch/sequence evidence with guard state; older sequence/epoch, wrong-domain,
stale, unavailable, uncertain or malformed evidence denies without fallback.
Repeated delivery of the identical current evidence may be allowed only while
its original freshness bound holds; conflicting same-sequence content denies.

Use exact decimal-to-integer conversion and conservative rounding for uncertainty,
not binary floating-point truncation. The reviewed source's system offset,
dispersion, delay, reference age and holdover policy must contribute correctly.
Local-reference mode and unsupported leap/source states fail closed. Numerical
limits stay explicit fictional inputs for offline tests; this proposal approves
no operational tolerance or claim of absolute reference-clock correctness.

## Suspend, restart and state compatibility

Monotonic freshness alone is insufficient. Prototype suspend-aware sampling with
bracketed read intervals, explicit collection skew and retained continuity
evidence. Reject observed suspend/reboot/domain changes or uncertainty that
cannot be bounded by the reviewed policy. Do not claim every physical suspend
can be detected below measurement resolution. That limitation must be resolved
in target-host policy before activation, not hidden by test thresholds.

Collector restart/epoch changes must not silently rebase consumers or clear a
latch. Preserve suspect evidence and require the existing stopped-generation
recovery process when continuity is uncertain. Keep the health trust generation
explicitly separate from assertion signing generation; any coordinated recovery
must inventory both rather than assume one key change fixes every boundary.

The current guard's v1 state/ClockHealth interface does not carry this complete
evidence. Build an inactive parser/provider first; design and test a versioned
state change before integration. Reject legacy/incomplete state, never auto-ALTER,
initialize or reset old trust during startup. Existing offline fixtures and
legacy interfaces must not become an operational fallback.

## Ordered deliverables if approved

1. Strict bounded evidence/daemon-response parsing and conservative uncertainty

2. Separate test signing/verifying and host/boot/generation/sequence/freshness
   negatives, including duplicate/conflicting/older evidence and collection
   timeout/output bounds. No real daemon or external time service.
3. Versioned retained continuity/suspend/epoch state and recovery tests, preserving

4. Inject the provider into the existing broker/authority/pre-bind and signed

5. Review the actual Linux host, source policy, numerical tolerances, encrypted

## First implementation checkpoint — 21 October

The inactive `apps/api/src/ciq_api/worker_health.py` implements bounded daemon
response parsing, explicit policy/binding/window models, temporary-key RS256
signing and strict stateless signature/domain/freshness/uncertainty checks.
All data and keys in tests are synthetic. No actual Chrony response was captured.

The pinned 4.7 CSV layout has fourteen fields, including both reference ID and
address. Layout/format behavior was checked against the upstream
[Chrony 4.7 client source](https://raw.githubusercontent.com/mlichvar/chrony/4.7/client.c),
not assumed from human-readable output. The source's
[tracking documentation](https://chrony-project.org/doc/4.7/chronyc.html)
defines the offset/delay/dispersion accuracy relationship and its reference-clock
assumption. The independent parser executes no upstream code or daemon command.
Future real collection still needs exact executable/version/transport acceptance;
a CSV field or signed format label does not prove the running binary's version.

The parser permits only configured canonical IP/refid pairs, normal leap status
and valid bounded fields. Local/unspecified/unapproved sources, multiple records,
oversized/non-ASCII output, malformed/non-finite/exponential numeric forms and
negative uncertainty deny. Exact rational arithmetic computes a ceiling of
absolute system offset + dispersion + half delay, with two additional ns for
the pinned seconds-format rounding, and rounds the reported skew upward. The
explicit fictional policy adds a conservative holdover rate; age and accumulated
uncertainty cannot be refreshed simply by re-signing the original old reference.
This is conditional processing of trusted measurements, not proof of UTC accuracy.

The envelope binds configured host/boot/health generation/collector epoch and
source, collection wall/monotonic/boottime intervals, reference age/error and
sequence. Signature verification uses the JWS layer, not ambient JWT expiry
time; issuer/audience and all fields are independently strict. Fixed RS256/header
shape, no key discovery, duplicate-key rejection, bounded message size and
canonical content hashing are tested. Collection/freshness comparisons include
suspend-aware timestamps and sampling-skew limits, but cannot establish retained
continuity or detect every physical suspend below measurement uncertainty.

**81 new tests pass; full API/DB 590 and root 175 pass**, with repository lint,
changed-file formatting and whitespace checks. A test-only ambient-clock mock
initially interfered with JWT signing; corrected by signing before installing
the verification clock trap, which now explicitly asserts no ambient-clock use.

**Not implemented/claimed:** executable collection/stream/time bounds, persisted
epoch/sequence conflict/replay rejection, versioned guard-state integration,
actual synchronization/host suspend policy, key/evidence delivery custody,
worker packaging or signed/mTLS integration with this provider. The checked
envelope deliberately has no `ClockHealth` adapter and must not authorize v1
guards. Repeated/older evidence can pass this stateless layer; retained sequence/
digest/latch enforcement is the next prerequisite, not waived by these tests.
Default routes/startup and existing guard/replay formats remain unchanged.
No Snowflake/AI, real credential, daemon installation, deployment, push or P3.

## Retained continuity checkpoint — 21 October

The inactive `worker_health_state.py` now adds a **separate version-2 SQLite
health-state prototype**, not a migration or replacement for the v1 nonce/clock
guard. Explicit test provisioning creates a new private file; normal acceptance
only opens existing state. It pins host, boot, health generation and collector
epoch, retaining sequence, canonical evidence digest, source-reference/collection
high-water marks and wall/monotonic/boottime observations. Assertion generation
and nonce state remain separate and unchanged.

An immediate transaction precedes sampling and signature/freshness checking.
Identical evidence is reusable only within its original freshness bounds.
Older sequence, conflicting content, regressing measurement timestamps, source
reference regression, observed clock rollback/suspend skew, excessive gaps and
unavailable/invalid evidence deny and commit a persistent unsafe latch before
raising. Subsequent connections cannot clear that latch. Wrong configuration,
legacy/incomplete/corrupt/missing state denies without attempting replacement.
Lock contention denies without sampling or reading evidence; there is no retry.

Tests exercise real temporary SQLite files, temporary RSA signatures and injected
fictional clocks. Reopened consumers and **separate Python processes** verify
that healthy repeated evidence and latched denial survive process boundaries.
This is not power-loss or filesystem custody acceptance. A trusted administrator
restoring the entire old file is still outside this prototype's protection.
Failed durable writes deny the current operation but cannot guarantee persistence
of a latch on broken storage. No automatic recovery/reset/migration is exposed.

This component still does **not** authorize tokens or adapt to `ClockHealth`.
Collector subprocess/stream/time bounds, unified clock/nonce-state design,
stopped-generation recovery integration, broker/authority/pre-bind/mTLS wiring,
packaging, trusted host policy and key/mount custody remain open. Injected
callbacks are not bounded host collection. No daemon, real key, runtime startup,
Snowflake call, deployment, push or P3 is included.

Verification: **23 new retained-state tests / 104 health tests** pass; full

## Bounded collection checkpoint — 21 October

`worker_health_collect.py` adds an inactive **offline-test-only collector**.
It requires explicit injected fake launcher and clock samplers; there is no
default `Popen`, real clock, signing key, startup path or CLI. Tests assert the
fixed candidate tracking request and substitute a disposable isolated Python
child emitting synthetic CSV. No Chrony binary, daemon or time service is used.

The fixed candidate request is `/usr/bin/chronyc -n -c -h 127.0.0.1 -p 323 tracking`.
It is a design candidate, **not an accepted installed path/version or operating
policy**. The [Chrony 4.7 manual](https://chrony-project.org/doc/4.7/chronyc.html)
documents tracking as monitoring, CSV/no-DNS options, explicit host/port and
the distinction between network monitoring and full-control Unix sockets.
The candidate specifies one literal loopback endpoint with no fallback; workers
receive neither that endpoint nor a daemon socket. Real host collection remains
separately gated, including version/binary custody and monitoring permissions.

The collector requests a separate process session, closed inherited descriptors,
null stdin, two pipes, no shell, fixed cwd and a minimal locale-only environment.
Nonblocking bounded reads retain at most the 2,048-byte permitted response plus
one overflow sentinel. Any stderr byte, oversized/empty/malformed/multiple CSV
records, non-zero exit, missing pipe or receive/wait timeout denies generically.
There is no retry or fallback, and diagnostics are not returned or logged.
One explicit fictional timeout (at most five seconds) is further capped by the
injected collection policy. Cleanup targets the test process's dedicated group,
closes both pipes and uses a bounded wait for the direct child. Tests cover a
descendant retaining pipes after its parent exits, plus a child closing pipes
while continuing to run. This is not a general subprocess sandbox: injected
launchers are trusted test code, escaped descendants and blocked OS operations
require real containment, and grandchild reaping is not established here.

Explicit samples bracket collection and cleanup. Boot changes, backward time,
observed suspend skew, excessive collection interval and missing samples deny
before a claim is returned. Collection returns unsigned validated evidence;
signing is a separate explicit step. An offline composition checks that such
signed evidence passes the retained consumer. A delivery-order regression also
fixes the consumer to sample **after** receiving evidence, not before a possibly
delayed callback; stale-on-delivery now latches rather than using an old sample.

Receive time includes completed launch duration and checks the end sample
against the deadline, but synchronous launcher/sampler calls cannot be forcibly
preempted here. Thus this is **not a hard end-to-end host deadline**. No operational
tolerances, real host health, replay authorization, v1 migration, worker wiring,
deployment or source activation are implied. Remaining gates include host
containment, unified health/clock/nonce lifecycle, stopped recovery, custody and
broker/authority/pre-bind/mTLS composition.

Verification: **26 new tests / 130 health tests**, full API/PostgreSQL **639**
and root **193** pass; repository Ruff, changed-file formatting and whitespace
checks pass. Browser/build/container/remote CI were not rerun. No Snowflake call,
account change, real credential, push or public deployment.
